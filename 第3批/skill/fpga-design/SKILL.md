# 通用 FPGA 项目设计

将需求转化为可以实现、验证和测量的硬件设计。根据当前任务从所需阶段进入，完成已请求的设计或实现；单模块任务不强制跑完整项目流程。适用于纯 FPGA 与带处理器的 SoC FPGA，也适用于控制、通信、采集、DSP、图像和计算等应用。

## 1. 明确设计目标与条件

从用户请求、已有工程、原理图和可用工具提取下面影响设计的条件；已知内容直接使用。只询问真正影响方案且无法查明的信息，其他缺失项写为假设，并继续不依赖这些信息的工作。

| 条件 | 需要明确的内容 |
| --- | --- |
| 功能与验收 | 输入输出、工作模式、正常／异常行为、可以检查的通过条件 |
| 数据与性能 | 格式、位宽、采样／帧／包速率、突发、吞吐、最大延迟、允许误差 |
| 硬件 | 板卡或器件及封装／速度等级、时钟、存储、引脚、电平、外设 |
| 工具与实现 | HDL 及版本支持、厂商工具、现有 IP、仿真器、授权和构建条件 |
| 工程限制 | 资源、功耗、成本、开发时间、可用测试设备及后续扩展需求 |

先检查前提是否成立：FPGA 是否确实适合；瓶颈是计算、搬运还是外设；要求的实时性、精度、带宽和资源是否能同时满足。独立指出冲突并给出替代方案，不为了使用 FPGA 而把所有功能迁入硬件。

选型、引脚、电气、硬 IP 和工具支持等具体结论，核查相应厂商数据手册、用户指南、板卡原理图和工具版本说明。没有来源时保留为候选或待确认项，不编造型号能力与管脚。

## 2. 按阶段加载指导

- **需求、选型、系统方案或算法硬件化**：读 [references/architecture.md](references/architecture.md)，确定数据流、并行度、数值精度、存储与接口预算。
- **RTL、状态机、总线或测试平台**：读 [references/rtl-verification.md](references/rtl-verification.md)，明确周期行为、接口契约和自检方式。
- **时钟／复位、跨时钟域、约束或时序不收敛**：读 [references/timing-constraints.md](references/timing-constraints.md)，先判断约束是否完整有效，再优化电路。
- **下载、联调或硬件现象排查**：读 [references/board-debug.md](references/board-debug.md)，用可观察的最小链路逐层验证。

复杂任务可以组合这些阶段；不要求每次读取全部参考文件。厂商专用 IP 和约束语法按实际工具处理，核心设计方法保持通用。

## 3. 执行设计闭环

1. **建立验收条件**：把“实时、稳定、高速、低功耗”等描述转成可检查的条件。条件暂不确定时给出参数化方案与限制。
2. **选择可实现架构**：先算数据率、周期预算、带宽、存储和位宽，比较串行复用、流水线和并行实现；优先采用满足指标且复杂度较低的方案。
3. **定义模块与接口**：明确时钟域、复位、握手、流控、数据格式、延迟、错误与超时；需要处理器时才划分软硬件职责，不预设 PC／PS／PL 结构。
4. **实现并同步验证**：先验证高风险算法、协议或跨时钟部分，再集成；优先复用已有合适 IP／模块，说明其配置、延迟和资源影响。交付实际可综合代码与对应的自检测试，不止给伪代码。
5. **综合、实现与闭环修正**：在可用工具中执行与任务匹配的检查；将锁存器、截断、未约束路径、时序及资源问题追到根因，再做有依据的改动。
6. **上板验证**：按已授权任务和可用硬件执行；先验证供电、时钟、复位与基本接口，再验证数据通路和性能。无法上板时保留明确的测试入口和判定方法，不声称已通过。

## 4. 始终保持的设计判断

- **并行与频率分开**：时钟频率、吞吐率、启动间隔和延迟是不同指标。理论并行度不能直接证明系统加速；考虑 DMA／总线、缓冲、主机和外设开销。
- **数值与时序分开**：算法参考结果正确，不表示定点精度、逐周期行为、握手或实现时序正确；分别验证。
- **同步与流控分开**：普通两级同步器不能保证多位数据一致；异步 FIFO 的跨域安全也不自动保证不会溢出。
- **仿真与实物分开**：RTL 仿真、综合、布局布线时序与实际硬件各有证据范围；没有工具、目标器件或测试设备时明确限制。
- **约束表达设计意图**：不使用无依据的 false path／multicycle、放宽频率或修改验收标准掩盖失败。
- **按影响范围验证**：小模块优先针对性自检，复杂接口加强随机流控和边界测试；不默认强制 UVM、形式验证或全量回归。

## 5. 结果应可直接使用

方案任务给出结构、关键计算、接口定义和取舍。实现任务提供 HDL、必要约束、可运行测试入口及实际检查结果。调试任务给出根因证据、修复和复测结果；尚不能确定时列出最有区分力的下一项实验。

说明哪些是已知条件、设计假设、理论估算、工具结果和板测结果。不能把资源估算写成综合利用率，把目标频率写成已达成频率，或把代码存在写成系统通过验收。
